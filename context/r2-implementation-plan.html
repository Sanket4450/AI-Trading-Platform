Release 2 · Research · Implementation plan

Trustworthy history before the first signal.

R2 turns Upstox historical market data into a complete, traceable 1-minute record for the current NIFTY 50 candidate pool and the NIFTY 50 index. The operator works from an index-ranked instrument catalog: select an instrument or a list, queue a fetch or refresh, and watch a persisted status move from not fetched to complete. Underneath, chunked fetches, raw payloads, strict coverage and a resumable backfill do the work. No strategy is evaluated and no order is sent.

What R2 delivers

Overview and scope

R1 proved the cockpit can exist without trading. R2 proves the history underneath it is complete, reproducible and honest about its gaps. Strategy work starts only after this gate passes.

Standing assumptions

  • Market timezone is Asia/Kolkata; stored instants are UTC timestamptz.
  • Upstox 1-minute history begins January 2022; later-listed instruments start later.
  • The access token is supplied manually in R2; OAuth and refresh arrive in R6.
  • Rate limits are 50 requests/second, 500/minute and 2,000/30 minutes per API per user.
  • One maximum of one calendar month per 1-minute historical request.
  • The initial backfill is an operator-triggered, resumable operation, not a cron job; it is launched from the catalog.
  • “Complete” is measured over the fixed 2022-01-01 → last completed session window, never over an implicit recent range.
  • Index membership is a reviewed snapshot with an explicit rank order; R2 does not store or display weights.
  • PostgreSQL 17+ is external; Redis is required for BullMQ and the distributed limiter.

The strict policy is intentional. R2 does not fill a missing minute with a flat bar. A synthetic bar would hide provider loss and corrupt the opening range, VWAP and volume confirmation. Time is converted once, at the edge

◷

Canonical time rules

  • Upstox candle timestamps are ISO-8601 with +05:30; parse the offset explicitly.
  • If an offset is missing, treat the value as IST, never UTC.
  • Store candle_start as UTC timestamptz.
  • Derive trading_date in Asia/Kolkata from candle_start.
  • Reject timestamps with non-zero seconds or milliseconds.
  • Compare the minute against the calendar session, not a hard-coded 09:15–15:30.
⌘

Identity rules

  • instruments.id is the only domain identity. Upstox keys live in mappings.
  • Resolve a provider row by (provider_id, external_key) first.
  • Then match an equity by ISIN; indices have no ISIN.
  • Then match exchange, segment and canonical symbol.
  • Only then create a new instrument.
  • Never key a candle, signal or backtest on an Upstox key.
typescript · the edge parser
export function parseCandleTimestamp(value: string): Date {
  const trimmed = value.trim();
  const hasOffset = /(?:Z|[+-]\d{2}:?\d{2})$/i.test(trimmed);
  const normalized = trimmed.includes(' ') ? trimmed.replace(' ', 'T') : trimmed;
  const withOffset = hasOffset ? normalized : `${normalized}+05:30`;
  const parsed = new Date(withOffset);
  if (Number.isNaN(parsed.getTime())) throw new Error(`Invalid candle timestamp: ${value}`);
  return parsed;
}

// IST business date, never the server's local date.
export function istTradingDate(instant: Date): string {
  return new Intl.DateTimeFormat('en-CA', {
    timeZone: 'Asia/Kolkata',
    year: 'numeric',
    month: '2-digit',
    day: '2-digit',
  }).format(instant);
}

Rules

  • from_date and to_date are inclusive; both are IST business dates.
  • The 1–15 minute intervals allow at most one calendar month per request. R2 uses one month, never a quarter.
  • Data starts January 2022. A request before that range is rejected by the planner, not sent.
  • The array order is not a contract. R2 sorts by parsed timestamp and rejects duplicates after sorting.
  • An empty array is a valid response. It becomes a coverage finding, not a silent success.
  • open_interest is the seventh tuple element; cash equities return 0 and R2 archives it, not stores it.
  • The daily oracle uses the same endpoint with days/1; one request can cover a decade.

Reference data bridge

Reference data is where silent corruption begins. R2 resolves identity by mapping first, repairs the tick-size unit, and treats the calendar and corporate actions as reviewed evidence rather than guesses.

Instrument identity and mappings Reference · daily How one Upstox row becomes one canonical instrument without creating a duplicate index. 4 rules

  3. Then resolve by exchange, segment and canonical symbol. This catches a first-time index or an instrument whose mapping was never created. It must not overwrite a different instrument with the same symbol on another segment.
  4. Only then create. Insert the instrument and its mapping in one transaction. A new instrument must have an exchange, segment, type, lot size and a valid tick size.

Instrument sync limit

R1 slices the segment-filtered set to 5,000 before applying any instrument-type whitelist, so it can drop needed rows and admit non-equity series. R2 filters to NSE_EQ with type EQ/BE and NSE_INDEX first, then applies a safety cap of 20,000. The observed filtered set is 3,080 rows, so nothing should be dropped.

◈

Mapping lifecycle

A mapping is versioned with valid_from and valid_to. If an ISIN changes, close the old mapping and insert a new one. If a symbol changes but the external key is stable, update provider_symbol and the canonical symbol with an audit row. Never reuse an old provider key for a different instrument.

Index membership and rank

▤

Reviewed membership snapshot

R2 seeds one universe, nifty-50, with selection_method='index_constituents'. Membership arrives as a reviewed CSV or fixture row set with universe_code, effective_from, rank, isin or symbol, source and notes. Import validates resolution, rank uniqueness and a 51-row total before writing a new instrument_universe_versions row and its members.

Rank 1 is the NIFTY 50 index; ranks 2–51 are the constituents in the reviewed order. Rank is display order only. No weight column is added, derived or shown in R2.

＋

Adding another index later

A second index is another instrument_universes row plus a new version and member set. The catalog filters by universeCode, so no schema change and no second status table are needed. An instrument can belong to more than one universe; its data status is per instrument, not per universe.

A membership change creates a new version with a later effective_from; the previous version is closed with effective_to, never edited. The catalog always reads the active version.

i
Membership is current, not historical. The nifty-50 version is today’s reviewed constituent list. It is not a point-in-time index reconstruction. R4 must not claim otherwise until a historical constituent series exists.

The rule never edits a candle and never creates an action automatically. It blocks a backtest preflight until a human confirms the action or dismisses the issue with a reason.

From HTTP response to evidenced row

Ingestion pipeline

Every chunk follows the same fifteen stages. The order is the guarantee: archive before parse, validate before write, reconcile before declaring coverage, and close the run with counts that match the database.

15 stages
Solid green is the write path. Dashed is evidence flow: raw payloads, quality findings and validation results. The operator surface reads the evidence; it never edits candles.

The fifteen stages

1 · Plan

Resolve scope and coverage

Turn the request into a list of instruments, session dates and month chunks. Reject dates before 2022-01-01 or after the last completed session. Skip chunks already marked succeeded unless the plan is a force refetch.

2 · Reference

Resolve provider and mapping

Find the Upstox provider, the primary mapping and the instrument's active window. A missing mapping fails the instrument, not the whole plan. The parent job records the failure.

3 · Chunk

Build inclusive month windows

Use the first and last calendar day of each month. A partial first or last month uses the exact request dates. Never request more than one calendar month for a 1-minute interval.

4 · Budget

Wait for a token

Acquire from the Redis-backed token bucket. The limiter enforces the second, minute and 30-minute windows before the request is sent, not after a 429.

5 · Fetch

Call Upstox once

Send the read-only historical request with a 60-second timeout. Classify the response by HTTP status and body. Do not parse a non-success body as candles.

6 · Archive

Store the raw response first

Compute the request fingerprint and payload SHA-256. Reuse an identical archive row; otherwise insert the raw JSON, byte count, HTTP status, retention class and expiry.

7 · Parse

Validate the envelope

Check status === 'success' and data.candles is an array. A schema failure is schema_invalid; it is not an empty month.

8 · Normalize

Tuple to canonical row

Parse IST with an explicit offset, convert to UTC, derive the IST trading date, convert prices and volume to decimal strings, and attach the run and raw payload IDs.

9 · Row validate

Reject what cannot be trusted

Check finite numbers, positive prices, OHLC bounds, non-negative volume, minute alignment, session membership, calendar trading day and duplicate timestamps. Every rejection becomes an issue with evidence.

10 · Reconcile

Compare with what is stored

Read the existing keys for the chunk. Identical rows are skipped. A final value that differs from a stored final value becomes a provider_revision issue before the new value is written.

11 · Write

Batch upsert

Insert in batches of 500–1,000 rows with a single conflict target. Update only when the incoming row is final or the stored row is not. Count inserted, updated, skipped and rejected separately.

12 · Oracle

Fetch daily OHLCV

For the instrument and date range, fetch the daily candles (one request per decade) into the raw archive. This is the independent witness for volume and prices; it is not a stored timeframe.

13 · Reconcile

Compare minute aggregate to daily

Aggregate the stored 1-minute rows and compare open, high, low, close and volume with the daily row. Store the result per instrument-day in the validation table.

14 · Coverage

Compute the verdict

Build the expected minute set from the session window, diff it against the observed set, find gap runs, and write market_data_coverage with strict status plus validation status.

15 · Close

Close the run and project

Update the ingestion run with counts and duration. Close the parent job only when all children finish. Refresh the materialized view once per batch, never once per chunk.

async function runChunk(input: ChunkInput): Promise<ChunkResult> {
  await rateLimiter.acquire();
  const response = await withRetry(() => client.fetchHistoricalCandles({
    instrumentKey: input.externalKey,
    from: input.from,
    to: input.to,
    unit: 'minutes',
    interval: 1,
  }));

  const raw = await archivePayload({
    providerId: input.providerId,
    endpoint: '/v3/historical-candle/:key/minutes/1/:to/:from',
    fingerprint: input.fingerprint,
    payload: response,
  });

  const parsed = parseCandleEnvelope(response);
  const normalized = parsed.candles
    .map((tuple) => normalizeCandle(tuple, input, raw.id))
    .filter((row): row is NormalizedCandle => row.ok);

  const valid = normalized.filter((row) => validateCandle(row).ok);
  const summary = await writeCandles(valid, {
    onRevision: (oldRow, newRow) => recordRevision(input, oldRow, newRow),
  });

  await reconcileDailyOracle(input, valid);
  await computeCoverage(input.instrumentId, input.from, input.to);
  await closeIngestionRun(input.runId, { ...summary, rejected: normalized.length - valid.length });

Batch write rules

  • Batch size 500–1,000 rows; one transaction per batch, not per row.
  • Conflict target is exactly (instrument_id, candle_start).
  • An identical row does not update updated_at; it counts as skipped.
  • A non-final row may be replaced by a final row.
  • A final row may be replaced by a newer final row only after a revision issue is recorded.
  • The run closes only after every batch is acknowledged.
◎

No silent drops

  • A rejected tuple increments rowsRejected and creates an issue.
  • An empty response is recorded as zero fetched, not as success without review.
  • A partial chunk failure closes partially_failed and leaves a retryable run.
  • The raw payload is always available for replay, even when the parser rejects it.
▲
Materialized view refresh is a batch operation. Refreshing after every instrument or chunk would rebuild the same view thousands of times. R2 refreshes once after a parent plan completes, once after the daily scheduled ingestion, and on demand. The view remains a cache, never a source of truth.

Rate limiter

◷

Three windows, one budget

A Redis-backed token bucket tracks the second, minute and 30-minute windows. A request acquires one token from all three before it is sent. The limiter is global to the provider, not per worker process.

  • UPSTOX_RATE_LIMIT_PER_SECOND=40
  • UPSTOX_RATE_LIMIT_PER_MINUTE=400
  • UPSTOX_RATE_LIMIT_PER_30_MINUTES=1600
  • UPSTOX_MAX_CONCURRENCY=4
↺

Backoff and circuit breaker

A 429 pauses the whole provider budget, not just one request. The pause honours Retry-After when present, otherwise uses exponential backoff with jitter. Five consecutive 429s open a circuit for two minutes; the job stays running and retries after the circuit closes.

A 401/403 opens no circuit: it fails fast with an actionable token or permission message. A 400 fails the chunk without retry because retrying the same invalid window cannot succeed.

Resume and stale-run recovery

Checkpoint

Completed chunks are skipped

A chunk with a succeeded run in the same plan is not fetched again. A new missing_only plan skips instrument-months whose coverage is already complete; a force plan refetches. A partially_failed chunk is retried because rejected rows may be fixable.

Crash

A running row is not a success

If the worker dies, the chunk remains running. A reconciliation job marks any run whose started_at is older than 15 minutes and whose heartbeat is stale as failed, then requeues it.

Restart

The plan resumes from the ledger

The instrument job scans its chunk list and starts at the first non-succeeded chunk. It does not restart the whole instrument or duplicate the completed batches.

Cancel

Cancellation is cooperative

A cancel request sets the parent job to cancelled. Child jobs check the flag between chunks, finish the in-flight chunk, and close with a cancellation result. No partial batch is left uncommitted.

Coverage algorithm

1

Build the expected set

Read the calendar row for the exchange and date. If it is not a trading day, write not_applicable. Otherwise generate one timestamp per minute from session_open inclusive to session_close exclusive.

2

Diff the observed set

Read candle_start for the instrument and window. The difference is the missing set. A missing first or last minute is a boundary finding; consecutive missing minutes collapse into a run.

3

Reconcile the volume

Compare sum(volume) with the daily oracle. A match proves the missing minutes had no trades. A shortfall proves lost bars. An excess proves duplicates or overlap.

4

Write both verdicts

One coverage row with strict status, validation status, gap metrics, daily/minute volume and evidence. The row is updated in place on every recheck.

◷

Applicability window

Coverage applies from max(2022-01-01, listed_on ?? plan_start) to min(last_completed_session, delisted_on ?? today). A missing date before a reviewed listed_on is not_applicable, not a gap. If listed_on is null and the provider returns no early bars, the early dates remain missing and raise coverage_shortfall; the first observed date is evidence for a reviewed listing-date correction, never an automatic lower bound.

⊘

Suspension and delisting

A suspended instrument-day is not_applicable with the suspension evidence. A delisted instrument stops at delisted_on; it is never deleted. If the master omits an instrument transiently, coverage remains missing and raises instrument_missing for review, rather than silently shrinking the denominator.

sql · gap runs for one instrument-day
WITH session AS (
  SELECT session_open, session_close
  FROM trading_calendar tc
  JOIN exchanges e ON e.id = tc.exchange_id
  WHERE e.code = 'NSE'
    AND tc.trading_date = $2
    AND tc.is_trading_day
), expected AS (
  SELECT generate_series(
    session_open,
    session_close - interval '1 minute',
    interval '1 minute'
  ) AS minute
  FROM session
), flags AS (
  SELECT e.minute,
         CASE WHEN c.candle_start IS NULL THEN 1 ELSE 0 END AS missing
  FROM expected e
  LEFT JOIN market_candles_1m c
    ON c.instrument_id = $1
   AND c.trading_date = $2
   AND c.candle_start >= (SELECT session_open FROM session)
   AND c.candle_start <  (SELECT session_close FROM session)
   AND c.candle_start = e.minute
), runs AS (
  SELECT minute, missing,
         row_number() OVER (ORDER BY minute)
       - row_number() OVER (PARTITION BY missing ORDER BY minute) AS grp
  FROM flags
)
SELECT min(minute) AS gap_start,
       max(minute) AS gap_end,
       count(*)::int AS minutes
FROM runs
WHERE missing = 1
GROUP BY grp
ORDER BY gap_start;

What could go wrong

Risks and guardrails

The dangerous failures are subtle: a 100× tick size, a duplicate index, a successful empty response, a partial final bar that looks final, or a rate limit that silently truncates the plan.

18 risks
1

Tick-size unit inversion

Risk: Upstox returns paise; R1 stored the raw value. Every stop, target and tick rounding is 100× wrong.

Guardrail: divide by 100 in the adapter mapping, validate 0 < tick ≤ 100, unit-test RELIANCE/HDFCBANK/MARUTI, and repair all seeded rows in Phase 1.

2

Duplicate NIFTY index

Risk: the provider symbol is NIFTY while the canonical seed is NIFTY 50; symbol-only matching creates a second index.

Guardrail: mapping-first identity resolution; a test with the real index row; a unique active exchange/symbol constraint plus a review check.

3

Token expiry mid-backfill

Risk: a multi-hour backfill crosses the token lifetime and fails halfway.

Guardrail: fail fast on 401, resume from the run ledger, refresh the environment token and retry failed chunks only. R6 replaces manual tokens.

4

Rate-limit suspension

Risk: four workers each think they can use 50 requests/second and the provider suspends the app.

Guardrail: one Redis-backed budget at 80% of every window; global pause on 429; no per-worker independent limiter.

5

Provider gaps

Risk: a successful empty or short response is recorded as success and a backtest runs on a hole.

Guardrail: strict coverage, gap runs, daily volume oracle and a preflight that rejects unexplained shortfalls.

6

Calendar fixture error

Risk: a wrong holiday or a missed Muhurat session marks 375 bars as missing or accepts a non-trading day.

Guardrail: reviewed fixture with source notes; Upstox current-year reconciliation; observed-boundary and non-trading-day checks; no automatic calendar edits.

7

Corporate-action surprise

Risk: an unconfirmed split creates a false breakout and a corrupted volume median.

Guardrail: reviewed CSV, confirmed-only adjustment, implied-factor detection and a critical preflight block until a human decides.

8

Duplicate or revision overwrite

Risk: adjacent chunks duplicate a boundary bar, or a refetch silently replaces a final value.

Guardrail: natural key on (instrument_id, candle_start); identical rows skipped; old/new values recorded as provider_revision before replacement.

9

Partial final bar treated as final

Risk: the 16:00 capture stores a partial last minute and the backtest uses it as a complete bar.

Guardrail: is_final=false, partial_bar info issue, T+1 historical replacement and a final-only read policy for strategies.

10

Raw payload and storage growth

Risk: 2,958 responses plus daily oracle payloads grow JSONB storage without a retention decision.

Guardrail: hash-based dedupe, retention classes, 12/24/90-day policies, byte accounting per run and partition monitoring.

11

Quality issue spam

Risk: one missing month creates thousands of per-minute issues and the operator stops reading the register.

Guardrail: aggregate per instrument-day, stable dedupe key, occurrence count and bounded samples. One real problem, one issue.

12

Resume/idempotency failure

Risk: a killed worker restarts the whole instrument, duplicates rows or double-counts volumes.

Guardrail: chunk ledger, succeeded-skip, stale-run recovery, exact conflict target and a kill/resume integration test.

13

Research mode bypass

Risk: a mode change or a stray route reaches the broker.

Guardrail: allowlist of offline/research; read-only adapter; no order route; no execution processor; orders verification; route inventory test.

14

Master truncation or bad filter

Risk: the 5,000-row cap or a segment-only filter drops a needed instrument or admits a government bond.

Guardrail: filter by segment and instrument type first, cap at 20,000, report excluded types, and assert the 51-instrument plan resolves.

15

Survivorship and membership drift

Risk: the current NIFTY 50 pool is treated as if it were the historical index, flattering a backtest.

Guardrail: label the dataset as a current-constituent candidate pool; use point-in-time liquidity selection; add historical constituent snapshots before R4 promotion.

16

Status lies

Risk: a successful HTTP call is shown as “Complete”, so an operator trusts a month the provider never delivered.

Guardrail: two persisted axes, a fixed precedence, complete only from coverage plus the oracle, and a test that a zero-row success renders as Missing, not Complete.

17

Duplicate fetch from repeated clicks

Risk: a double-click or a second operator creates two plans for the same instrument and doubles provider usage.

Guardrail: a partial unique index for one active backfill run per instrument; the second request returns the existing run ID; the UI disables the action in queued/fetching states.

18

Index order drift

Risk: the catalog order slowly diverges from the reviewed index because someone edits rows or trusts a provider list.

Guardrail: membership only through a versioned reviewed import; rank unique per version; the catalog reads the active version and never sorts by insertion order.

▲
Retention decision to confirm before the full backfill: keep every 1-minute candle while the backtest programme is active; keep standard raw payloads for 12 months, extended master/daily payloads for 24 months and error payloads for 90 days. Detach a cold partition only after a documented archive copy.

What “done” means

Acceptance and definition of done

R2 is accepted when the history is complete enough to trust, every exception is explained, the run can survive a restart and the system still cannot place an order.

Research gate
✓

Definition of done

  • A fresh setup starts with TRADING_MODE=research and refuses paper/live.
  • 51 instruments resolve to canonical IDs; tick sizes are correct; the NIFTY index is not duplicated.
  • The nifty-50 universe version holds 51 ranked members from a reviewed source; rank 1 is the index; no weight is stored or displayed.
  • The catalog lists 51 rows in rank order with a persisted fetch status and data status.
  • A per-instrument or multi-select fetch creates exactly one plan; a second request while active returns the existing run.
  • Status survives a worker restart; succeeded is never displayed as complete; a delayed recompute shows as Verifying.
  • A missing_only refresh skips months whose coverage is complete.
  • The NSE calendar covers every date from 2022-01-01 through 2027-12-31, including special sessions.
  • Every available 1-minute bar is stored for the scope, with raw payload and run lineage.
  • Every trading instrument-day has a coverage verdict and, where possible, a daily validation verdict.
  • Every partial or missing day has an issue, a rule, evidence and a decision.
