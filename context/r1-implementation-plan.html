What R1 delivers

Overview and scope

R1 is the release that makes the system trustworthy before it makes it profitable. The database is fully modelled now so later releases add behaviour, not structural rewrites.

Offline
◆

In scope

  • Application foundation: API, worker, web, shared packages and health checks.
  • Complete PostgreSQL schema for the full trading lifecycle, migrated in R1.
  • Broker-neutral instrument reference data with Upstox provider mappings.
  • 1-minute candle storage, coverage tracking and derived timeframes.
  • Immutable, versioned strategy and risk configuration snapshots.
  • Operator dashboard for system health, data coverage, configuration and audit.
  • Seeded operator, one active account, NIFTY 50 and the 20-stock ORB universe.
  • Offline trading mode enforced by configuration and by the absence of order code paths.

  • Live or paper order submission, fills and broker callbacks.
  • Historical data ingestion beyond a small verification backfill (R2).
  • Strategy evaluation and signal generation (R3).
  • Backtest execution engine and promotion decisions (R4).
  • Live feeds, risk enforcement and order-state management (R5).
  • Production authentication against Upstox, static IP and compliance setup (R6).
  • Futures, options, Greeks or derivative risk. Instruments are cash equities and indices only.

Standing assumptions

  • Cash equities and indices only: NSE/BSE EQ, BE, ETF and index instruments.

04

Rules the schema must keep

Design principles

These are the invariants that keep the model maintainable when data sources, strategies and execution modes change.

10 rules
◎

1 · Broker-neutral identity

Every domain row references instruments.id. Vendor keys, tokens and symbols live only in instrument_provider_mappings. A provider change never touches orders, candles or signals.

◈

2 · Normalized plus raw

Typed columns answer product questions. raw_provider_payloads preserves the original JSON so a parser bug is a replay, not a re-fetch.

▣

3 · Configuration is immutable

A configuration version is never edited. A change creates a new row with a new hash and a later effective date. History is the primary record.

↯

4 · Events are append-only

order_events, position_events, audit_log and domain_events are append-only. Current state is a projection, not a replacement for history.

⛓

5 · Explicit many-to-many

Every M:N relationship has a named join table with its own columns, constraints and indexes. The ORM never owns a hidden join table.

⌘

6 · Idempotent ingestion

Natural unique keys — instrument plus candle start, account plus broker trade ID, provider plus external key — make retries safe.

◷

7 · Time is explicit

Instants are timestamptz in UTC. trading_date is a separate IST business date. Market sessions come from trading_calendar, not application guesses.

▤

8 · Partition at volume

1-minute candles and quote snapshots are range-partitioned by month. Queries prune partitions by instrument and time before touching rows.

✦

9 · Exact numbers

Never float for prices or P&L. Prices use numeric(20,4), money numeric(20,2), ratios numeric(20,10).

⌫

10 · Delete only what is disposable

Reference and audit rows are never hard-deleted. Operational rows use status flags. Cascades are limited to sessions and child events.

i
Secrets are write-only. The API can create and rotate broker_credentials, but it never returns encrypted_value. The encryption key comes from CONFIG_ENCRYPTION_KEY; losing it means re-authenticating with Upstox, not losing trading history.

Many-to-many · users ↔ accounts

Access is not a column on either table. user_account_access is the independent join table, and it carries the role, grantor and expiry that the relationship needs.

One-to-many on both sides, never a direct many-to-many. Deleting a user or account removes the grant row, but the audit_log record of the grant remains because it stores the identifier and redacted state, not a cascading foreign key.

Many-to-many · accounts ↔ instruments

Tradability is a relationship with rules: a boolean, a product allowlist, quantity caps and an effective window. That is why it needs an independent table rather than an array on either side.

The pre-trade chain reads this table, not the universe alone. Being in a strategy universe selects an instrument; this table confirms the account is actually allowed to trade it, in the chosen product, within the quantity cap and on the effective date.

Many-to-many · universe versions ↔ instruments

A universe has many instruments and an instrument can sit in many universes. The independent table is instrument_universe_members; it carries rank, the liquidity metric and its own validity dates.

Membership is snapshotted, not mutable. A weekly selection creates a new universe version and a new set of member rows. Backtests can therefore ask for the exact universe that existed on a historical date without reconstructing it from today's list.

Deriving higher timeframes

Every timeframe is a deterministic aggregation of the same 1-minute rows. The examples below are the canonical queries the strategy package will use; they are not stored objects.

sql · 5-minute rollup
WITH bars AS (
  SELECT
    instrument_id,
    date_bin('5 minutes', candle_start, '2000-01-01 00:00:00+00') AS bucket_start,
    candle_start, open, high, low, close, volume
  FROM market_candles_1m
  WHERE instrument_id = $1
    AND candle_start >= $2
    AND candle_start <  $3
)
SELECT
  instrument_id,
  bucket_start,
  (array_agg(open  ORDER BY candle_start))[1] AS open,
  max(high) AS high,
  min(low)  AS low,
  (array_agg(close ORDER BY candle_start DESC))[1] AS close,
  sum(volume) AS volume
FROM bars
GROUP BY instrument_id, bucket_start
ORDER BY bucket_start;
sql · 15-minute opening range (09:15–09:30 IST)
SELECT
  max(high) AS opening_range_high,
  min(low)  AS opening_range_low,
  sum(volume) AS opening_range_volume
FROM market_candles_1m
WHERE instrument_id = $1
  AND candle_start >= timestamptz '2026-10-23 09:15:00+05:30'
  AND candle_start <  timestamptz '2026-10-23 09:30:00+05:30';
sql · approximate intraday VWAP
SELECT
  sum(((high + low + close) / 3) * volume) / nullif(sum(volume), 0) AS vwap_approx
FROM market_candles_1m
WHERE instrument_id = $1
  AND trading_date = $2
  AND candle_start < $3;  -- decision timestamp
▲
VWAP is an approximation from 1-minute bars. True VWAP requires tick or trade-level data. For live decisions, prefer the exchange average_price in market_quote_snapshots; for historical replay, use the typical-price approximation and document it in the strategy report so backtest and live results are compared honestly.

Many-to-many · strategy versions ↔ configuration versions

A configuration snapshot can be reused by several strategy versions, and a strategy version can bind parameters, risk and execution separately. The independent table is strategy_config_bindings.

Reuse without mutation. The same risk snapshot can be bound to multiple strategy versions, and the same strategy version can keep separate parameter and execution snapshots. The binding row records the role and who approved it, so “which settings were live?” is a join, not a reconstruction.

Many-to-many · strategy versions ↔ instruments

The strategy's tradable universe is explicit membership, not an array. strategy_universe_members carries rank, validity and optional provenance back to the weekly universe snapshot.

The strategy never reads the universe definition directly. It reads its own membership rows for the session date. That makes a backtest reproducible: the same strategy version, date and membership rows always produce the same candidate list.

Many-to-many · strategy versions ↔ accounts

strategy_activations is the explicit join between a strategy version and an account. It carries the mode, lifecycle state and pinned risk snapshot, so a strategy-to-account relationship is never implicit.

An activation is a relationship, not a column. It is mode-specific, has its own lifecycle, and pins the risk snapshot. The partial unique index guarantees at most one active activation per strategy version, account and mode, which prevents a second signal loop from starting silently.

Trading lifecycle

Every arrow is a one-to-many or one-to-one relationship. The broker snapshot is compared with the internal position; it never replaces it. The closed trade is derived from confirmed fills, not from intended prices.

All relationships are one-to-one or one-to-many. A signal has one risk decision and many orders; an order has many events and many fills; a fill belongs to one order and has one cost row. The broker snapshot (dashed) reconciles the internal position but never becomes its source. Round-trip P&L uses confirmed fills and costs, not signal prices.

How rows move

Data flows

Five flows cover the lifecycle. R1 implements the first and the fifth; the rest are specified so the schema is used correctly when their code arrives.

5 flows
Archive first, normalize second. If the parser is wrong, the fix is a replay from raw_provider_payloads, not another provider call. The dashboard reads coverage and issue tables, not the raw payloads.

1 · Historical ingestion (R1/R2)

Scheduler

Enqueue a bounded job

Create job_runs and market_data_ingestion_runs with provider, instrument, unit, interval and date window. Reject a window outside January 2022 or beyond today. Chunk requests to the provider limit — one month for 1–15 minute intervals — and record every chunk as its own run.

Adapter

Fetch and archive

Call Upstox V3; store the response in raw_provider_payloads before parsing. Record HTTP status, request fingerprint and expiry class.

Normalizer

Validate each candle

Parse timestamps as IST, convert to UTC, check OHLC invariants, volume and duplicates. Reject invalid rows into data_quality_issues; do not silently drop them.

Writer

Upsert idempotently

Write to market_candles_1m on (instrument_id, candle_start). Repeated ingestion updates updated_at, never duplicates.

Coverage

Prove completeness

Recompute market_data_coverage for each instrument and date. Expected 375 bars for a normal session; special sessions come from trading_calendar.

Projection

Refresh the daily view

REFRESH MATERIALIZED VIEW CONCURRENTLY mv_instrument_daily_stats after the batch, then close the job and ingestion run with row counts.

2 · Signal to execution (R3–R5)

Context

Resolve the live configuration

Load active strategy_activations for the account and mode. Resolve the bound configuration version and the strategy universe members effective on trading_date.

Market data

Derive the decision bars

Read 1-minute candles and roll up 5-minute bars. Compute opening range, VWAP, NIFTY EMA confirmation and volume ratio. Reject stale data before evaluating rules.

Signal

Persist the decision

Write signals with the decision bar, entry/stop/target, requested quantity and full evidence JSON.

Risk

Approve, reduce or reject

Write exactly one risk_decisions row. Apply account permissions, 0.5% risk, 1% daily loss, one open position and two entries per day. A rejection ends the flow.

Broker

Submit and track

Create orders, then append every broker transition to order_events. A unique client_order_ref makes retries safe.

State

Apply confirmed fills

Write fills, compute trade_costs, append position_events, project positions, and on exit create or close round_trip_trades.

3 · Reconciliation (R5–R8)

Snapshot

Fetch the broker's truth

Capture orders, trades, positions, holdings and funds into their snapshot tables with raw payload links.

Compare

Match by stable keys

Orders by (account_id, broker_order_id), fills by (account_id, broker_trade_id), positions by account, instrument, product.

Record

Write issues, not guesses

Every field difference becomes a reconciliation_issues row with internal and broker values. The run status becomes mismatched.

Gate

Block new entries on critical drift

Raise a critical risk_events row. The pre-trade gate refuses new entries until the issue is resolved.

4 · Backtest (R4)

Request

Pin inputs

Create backtest_runs with strategy version, configuration version, dataset boundaries, capital, cost model and slippage model.

Windows

Partition chronology

Create backtest_windows for development, validation, holdout, walk-forward and stress. Never tune on the holdout.

Replay

Simulate conservatively

Read only candles at or before the decision timestamp. Apply bid/ask spread, slippage, rejection and the cost model. Write backtest_trades.

Results

Store curve and metrics

Write one backtest_equity_curve point per trading day and the full backtest_metrics set.

Governance

Review the gates

Create strategy_promotion_reviews with thresholds and observed results. A failed gate blocks activation; a waiver needs a written reason.

5 · Configuration change (R1)

Draft

Validate the payload

Validate against strategy_versions.parameter_schema or the risk schema. Reject unknown keys and out-of-range values.

Persist

Create a new version

Insert configuration_versions with a canonical JSON hash, effective_from and supersedes_id. Never update an existing row.

Bind

Attach it to a strategy version

Insert strategy_config_bindings with a role. The binding is the only way a strategy sees the snapshot.

Apply

Next session, not mid-session

Risk-increasing changes take effect from a later effective_from. The current trading_sessions.configuration_version_id remains pinned.

Audit

Record who and why

Write audit_log, the payload hash and the binding author. The dashboard links the change to every signal and trade that used it.

What could go wrong

Risks and guardrails

The dangerous failures are not syntax errors. They are silent data drift, timezone mistakes, mutable configuration and a system that thinks it is offline but is not.

12 risks
1

1-minute storage growth

Risk: 20 instruments over five years is roughly 10 million rows; a larger universe multiplies it.

Guardrail: monthly partitions, BRIN on time, BRIN-friendly append pattern, no per-row updates except finalization. Monitor partition size and archive detached partitions after the retention decision.

2

Pre-2022 history gap

Risk: a backtest quietly starts before January 2022 and produces a shorter sample than intended.

Guardrail: ingestion rejects earlier dates; backtest_windows validates dataset_from >= 2022-01-01; coverage preflight blocks runs with missing bars.

3

Timezone drift

Risk: Upstox order timestamps have no offset; parsing them as UTC shifts the whole session.

Guardrail: one shared parser treats broker timestamps as Asia/Kolkata; contract tests assert the UTC result; trading_date is always derived in IST.

4

Corporate-action errors

Risk: an unadjusted split creates a false breakout, a fake stop and a corrupted volume median.

Guardrail: corporate_actions.status must be confirmed before factors apply; ex-date queries apply factors on read; a mismatch raises a quality issue.

5

Provider key reuse

Risk: an exchange token is reused after expiry and a mapping silently points at the wrong contract.

Guardrail: canonical UUID identity; mappings are versioned with valid_from and valid_to; Upstox instrument_key is the external key, not exchange_token.

6

Duplicate ingestion

Risk: a retried job doubles candles, fills or trades and corrupts P&L.

Guardrail: natural unique keys on candles, fills, trades and mappings; upserts on those keys; ingestion run counters expose rejected duplicates.

7

Credential leakage

Risk: an access token appears in a log, an error payload or an API response.

Guardrail: AES-256-GCM ciphertext in broker_credentials; write-only API; redaction at the logger; key version for rotation; audit access to the table.

8

Mutable configuration

Risk: an operator “fixes” a setting in place, making yesterday's trade irreproducible.

Guardrail: no update path for configuration_versions.payload; create a new version; a database trigger rejects payload updates; signals and trades keep the version ID.

9

Offline mode bypass

Risk: a worker or route reaches the broker while the system claims to be offline.

Guardrail: mode assertion at startup, no order routes, no execution queue in R1, adapter allowlist limited to read-only endpoints, e2e test asserts absence of order controls.

10

Reconciliation drift

Risk: internal positions differ from the broker and the system keeps trading on a wrong view.

Guardrail: daily and intraday snapshots; field-level issues; critical mismatch raises a risk event and blocks new entries until resolved.

11

Implicit many-to-many regression

Risk: a future ORM model adds a hidden join table and the architecture stops being visible.

Guardrail: every M:N has a named table in the schema and a diagram here; code review checks relationships; Drizzle schema exports only explicit tables.

12

Raw payload exposure

Risk: archived payloads contain account identifiers, tokens or personal data and become a shadow dataset.

Guardrail: redact request params, restrict table access to the worker role, retention classes, no raw payload in API responses, encrypted database at rest.

▲
Retention policy to confirm before R7: keep all 1-minute data from 2022 onward while the backtest programme is active. After the holdout is retired, move pre-2024 partitions to cold storage rather than deleting them. Quote snapshots can be pruned after 90 days; raw standard payloads after 12 months.

Relationship invariants

⛓

Cardinality you can rely on

  • No direct many-to-many relationship exists anywhere; every M:N is a named table.
  • One signal has exactly one risk_decisions row.
  • One fill has exactly one trade_costs row.
  • One account, instrument and product has at most one open position.
  • One strategy version, account and mode has at most one active activation.
  • One account, date and mode has exactly one trading session.
  • One instrument and date has exactly one coverage row.
  • One instrument and provider has at most one primary mapping.
  • One provider and external key has at most one current mapping.
  • One run and metric key has exactly one value.
▤

Immutability you can rely on

  • configuration_versions.payload is insert-only.
  • strategy_versions are insert-only after release.
  • order_events, position_events, audit_log and domain_events are append-only.
  • raw_provider_payloads are never updated; only retention deletion.
  • trading_calendar may be corrected, but historical sessions remain referenced by snapshots.
  • instruments are retired with is_active=false and delisted_on, never deleted.
  • accounts are disabled, never deleted.
  • Financial rows are never hard-deleted.
